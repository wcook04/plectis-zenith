## Execution and evidence

Select recent, capable, inexpensive Chinese-developed models using current official metadata and actual endpoint prices. Price ceilings are $0.50 input and $1.50 output per million tokens, with no per-request fee or expensive fallback. Independent trials may use bounded concurrency: at most three calls across this host and one per pinned endpoint. Keep dependent calls ordered, fix the route within paired comparisons, reserve shared budgets atomically, and drain active calls before a checkpoint or stop. Legacy callers remain serial. Size authorized campaigns to answer the research question within a declared budget; they need not be tiny. Bind reasoning settings into request identity and retain all billed tokens.

Use existing providers, budgets and source custody. Freeze source, datasets, evaluator, model and comparison protocol before inference. Preserve original attempts; no automatic retry or manual repair of model output. A deliberately changed interface starts a separately versioned experiment. Never commit credentials or private transport records.

Lab executes the exact procedure. Oracle receives measured evidence, including a rejected candidate's source and execution errors, not just incumbent outcomes. Evolve proposes a replacement. Replay the complete development set before selecting an experimental incumbent, and keep held-out outcomes out of repair prompts. Record unchanged programs, rejected proposals and regressions. Test the actual delivery into the next provider request.

A scoped numerical conclusion can be unresolved while independent findings remain established. Quantity semantics, units, population and multiplicity must survive composition. Model-authored scope and explanations are hypotheses, not certified invariants. A changed action or passing schema does not establish a correct diagnosis.

## Public explanations

Every paper edition must retain an explicit first-page account of AI use and the limits of human review. Use the established disclosure in `paper/zenith.tex`; do not replace it with a vague claim of assistance or imply independent human verification. The website projects this statement from the manuscript. Verify it in the rendered PDF and web edition before publication, alongside the three-page limit.

Write website copy, headings, tooltips and README introductions for someone who has never used Zenith or written a program. State who does what to which program or input. When saying a check passed, explain the comparison or requirement and what that result establishes. A valid output format does not prove a prediction correct; agreement on selected inputs does not prove correctness for every input. Define terms at first use: a run is one saved execution, a node is a data source or program step, a graph arrow means one step reads another's output, and a receipt is a saved result record. Explain task-specific terms such as profile, qualification, protected evaluation and source hash before using them to describe a result. Prefer the ordinary explanation in navigation labels.

Review the complete rendered page, including expanded results, errors and diagrams; a word blacklist is not a clarity check. Preserve technical IDs, exact saved evidence, counts, comparison groups and limitations. Read the humanizer skill when available, and record substantive ambiguous-to-literal examples in the change description. Check that source links, result withholding and research qualifications still work after editing copy.

For repository layout changes, preserve source-compatible paths and run `python scripts/check_structure.py` with `tests/test_structure.py`. Document new source roles in README.md and docs/architecture.md.
