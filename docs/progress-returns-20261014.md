# Nineteen PROGRESS returns: preserve the question, check its scope

Nineteen researched PROGRESS return ZIPs arrived, numbered **02–20**. A researched return for inquiry 01 was not supplied; its original inquiry packet is a different artifact. We independently rehashed all supplied return ZIPs against the intake receipt; every digest matches. The archives contain **1,443 regular files**, including 19 manifests and 1,424 manifest-listed payloads. The intake's 1,818 `rglob` entries also count 375 directories; it is not a file count. The companion [custody and decision record](progress-returns-20261014.json) gives each archive's exact name, SHA-256, byte size, regular-file count and disposition. The original returns are exposed research material, not nineteen independent confirmations or instructions to install their proposed architecture.

The returns converge on one useful retained unit: a **scoped, executable investigation procedure**. It binds a source, program and client obligation; proposes a bounded question; records the independently measured answer; and says when that question, answer or candidate revision needs revalidation. Ordinary code, tests and source-bound receipts are enough to represent it. A graph can help inspect dependencies, but these returns do not show that a reporting graph outperforms a competent ordinary code-and-test archive with the same history.

The strongest result remains narrower than the broad aspiration. Retained continuation questions improve later extraction **within one authored joint learner** when both arms begin with the same answer cache. Yet ordinary separate modules use fewer teacher calls over the complete six-source workload. Later eager transfer of all questions into those modules hurts five of six targets. An authored rank sieve reduces the ordinary target acquisition bill from 3,071 to 3,039 calls on those exposed functions, a 1.04% saving, but wins only three of six targets and was designed after inspecting them. A later gated variant costs 3,078, slightly more than cold ordinary acquisition. The evidence supports keeping useful questions and testing when to use them; it does not establish a better overall learning architecture.

## What changed the research decision

The earlier native pilot's fixed tester scores **239/288** on confirmation, versus **216/288** for ordinary model-written investigation and **218/288** for the diagnostic variant. The policy-delivery audit explains part of the gap without excusing it: twelve generated selectors produced seven valid new probes, 51 duplicate proposal slots and three interface failures. Eight policies never read runtime inputs; two solved the LRU parent task instead of selecting an experiment. One generated `[224,128]` UTF-8 question exposed a real native/parent discrepancy even though its explanation falsely called the bytes a NUL encoding. The host measurement, not the note, supplies evidence. All three defective parent episodes already failed visible examples, so the existing campaign cannot isolate repair value from newly discovered evidence. Returns 06, 14, 16 and 17 point to a small next protocol: make the experiment-selection role explicit, host-deduplicate bounded proposals, and compare direct requests with policy-code generation while charging every attempt. They do **not** establish that a new request channel improves model behavior. [Current native method and original results](conformance-study.md).

Return 17 also recovers one SQLite question already constructed inside a failed selector: changing its action wrapper retrospectively makes a legal native probe that returns next ID **6** where the parent returns **9**. This demonstrates an interface-blocked useful question in that exposed case. It is not evidence that a new prompt would cause the model to deliver the same question, or that the question would be the first evidence of the defect.

Return 16's standards-informed ordinary UTF-8 tester finds semantic first failures in all three faulty episodes using 29 native calls, the same call count as the original fixed pack, which finds only one semantic first failure. It has a stronger retrospective specification prior, so it is a challenge with different prior information rather than an equal-prior win. It makes ordinary boundary testing an essential future rival. Return 14's authored conditional tester uses 4,527 calls on 512 later synthetic samples, beating several weak fixed rules, but same-history ordinary exhaustive search and a predeclared two-probe heuristic also use 4,527. Its 1,536 initial source calls and local policy search count too.

Returns 07–11 identify different reasons a local repair can fail. A readout can ignore retained state; a proposed interface can truly discard information; two supplier requirements can conflict only when forced into one compilation unit; a model can get a valid prefix wrong, a completed scalar wrong, or the time at which a failing call commits output wrong. Return 10 makes consumer-relative sufficiency tangible: percent-decoding `%` and `%25` produces the same current output `%`, but appending `41` requires different next outputs. These distinctions lead to different actions: change code, preserve state, narrow a boundary, measure a contrast, or reconstruct from the evidence. The executable examples are valuable because the proposed action is checked against the actual source and all affected consumer obligations. Their positive repairs were authored and matched by ordinary CMake, source-boundary testing, archive adaptation, cold enumeration or memoised code, so they are fixtures for acquisition tests rather than acquired graph capability.

Return 09's repair audit also corrects a misleading count: ten of eighteen returned programs are byte-identical to their parents, but nine of those parents had no observed defect. Among the nine proposals with a known failing parent, three improve without losing a measured success and two close every known failure. Selection on a tie is incumbent management, not a successful repair. The reconstruction that passes 1,504/1,504 authored diagnostic cases is matched by an ordinary adapter to a previously supplied transition reference and by cold search of the same authored family.

Change creates a further obligation. Return 11 executes a SQLite upgrade where the same BLOB bytes produce 3456 under the old JSON interpretation and 456 under the new. A producer's missing format declaration cannot be recovered from the downstream bytes or engine, even with unlimited further engine queries. The small authored reuse wrapper scores 300/300 with 100 new statements, but ordinary memoisation ties it and canonical client code has a better lifetime native-call count. An upgrade that passes fresh-value canaries can still roll back an open transaction; a rolled-back savepoint can still alter `last_insert_rowid()`. Thus a retained experiment needs conditions and effects, and a retained answer needs an obligation and source binding. The next result must show a learner acquiring a retention or recovery rule *before* information disappears, not merely executing this supplied one.

## Protocol chosen from the returns

The chosen first stage was the [investigation-interface diagnostic](progress-protocol-20261014.md). It pairs repair-only, fixed, legacy selector, direct finite-plan, outcome-aware two-turn and outcome-masked two-turn arms on fresh but still within-family parents. Its job is to establish that a direct model request can deliver a distinct legal second question and that measured feedback changes the next question or repair at a cost worth paying. Qualification and diagnostic populations remain separate; failure leads to a separately versioned interface repair. A positive result here is a delivery and local investigation result, not transfer or a new learning algorithm.

After that delivery gate, the broader research target is a client task with a changed dependency, interruption or recovery boundary whose success can be checked independently. Start from the **same source, visible failures, ordinary tools, edit authority and history** for the procedure condition and a capable ordinary coding/testing condition. Keep a fixed tester and direct native/reference use where allowed. Freeze the acquired procedure and selection rule before later clients or mechanisms appear. Charge initial discovery, failed proposals, test execution, retrieval, storage, model calls, migration interruption and false refusals. The procedure must choose a useful *new* measurement or retention action, revise the program or invocation when warranted, and preserve earlier measured client successes. Later tests should include an already-correct program, a case where the old question is invalid, an absent authoritative declaration requiring refusal, and an ongoing execution where restarting loses work.

Return 20 supplies one suitable *development fixture*: three authored SQLite batch clients satisfy **30, 135 and 240 of 240** enumerated caller-state contracts as the code moves from partial writes through overbroad rollback to a correctly scoped savepoint. A tiny authored tester can find both defects. This demonstrates checkable client obligations and a stronger ordinary control, not a learned repair or unseen project result.

A positive result would be lower **lifetime cost to correct, independently checked continuation or repair**, beyond the same old answer cache and a same-history ordinary code repository. If an ordinary canonical value, native call, fixed boundary tester or source-aware cache ties it, use that simpler implementation. This is the falsifier that gives the retained question scientific value.

## Verification boundary

All 19 original ZIP hashes were recomputed and matched the intake list. Every one of the 1,424 manifest-listed payloads was checked for ZIP membership, byte size and SHA-256. The nineteen pasted summaries were reconciled with archive names and packet evidence; summary prose supplies no independent measurement. Offline return replays use **no paid inference** and test the authors' exposed artifacts. They are not a rerun of the historical model campaign, a fresh-clone installation check or prospective confirmation. The companion JSON records each return's reproduction scope; the individual return manifests, sources and saved receipts remain the numerical authority for their own claims.

For the early learner returns, 02's quick suite and maintained native demo reproduced the witness-cold and generic-singleton call vectors, while its exact original full replay requires the archived Python/SQLite pair. Return 03 matched 14 deterministic reports; 04 matched six semantic and five byte-exact reports and rebuilt its large snapshot audit; 10 matched four semantic output files. Their environment-bound metadata varies across Python versions. Return 05's pure recipe derivation and packet custody checked, but its full XML/Node replay was blocked by missing `lxml` on this host. The installed learner is an exact-class diagnostic; its finite UTF-8 and SQLite panels retain failures.
